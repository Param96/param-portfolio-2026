# Production SEO audit, 17 November 2026

## Root causes and live evidence

| Finding | Evidence |
| --- | --- |
| Clerk's development handshake interrupts public requests without its browser state | Independent public fetches of the apex homepage, blog, contact, research and the published Meadow article were redirected to a Clerk development instance with `dev-browser-missing`. The installed Clerk SDK reproduced the redirect for both Googlebot and Chrome user agents using the previous proxy. The revised proxy allows those requests through to Next.js rendering. |
| Vercel is serving a different source revision from this checkout | The [active production deployment](https://vercel.com/param96s-projects/param-portfolio/7ZkLkerdZv6jFvUgNPHwuMqPZVGn) shows branch `master`, commit `c8edca6`, Ready, and a 33-second build with six warnings. This checkout uses `main` at `2c91f3f`, which has the October SEO repair. Production robots.txt and sitemap responses still exhibit behaviors that repair addressed. The full active `master` commit was unavailable in the local Git object store. |
| Google's historical exclusion is specifically an HTTP header | The stored homepage inspection says Googlebot smartphone successfully fetched the page on 18 August 2026 and found `noindex` in `X-Robots-Tag`. Crawling was allowed and Google recorded the apex user-declared canonical. No Google-selected canonical was shown. The deployment or edge rule that generated that historical header could not be established. Vercel documents automatic `noindex` on previews and outdated production deployments, which is a possible explanation only if a request reached such a deployment. [Vercel response headers](https://vercel.com/docs/headers/response-headers) |
| The current browser response differs from Google's stored crawl | Chrome DevTools recorded HTTPS www returning `308` directly to the apex with the query preserved, followed by an apex `200` served by Vercel. Neither response contained `X-Robots-Tag`. The apex homepage source contained one `index, follow` robots tag and one canonical pointing to `https://parampatel.in`. The earlier stateless fetch reported the Clerk redirect. The successful browser session and the stateless response test cover different request states. |
| Current production sitemap timestamps are misleading | Chrome displayed valid sitemap XML containing the six landing pages and the published Meadow article. All six landing pages carried the same fresh timestamp, which the older repository implementation generates on every request. The article had its own CMS timestamp. The current checkout already omits generated dates for landing pages and uses valid CMS dates for articles. |
| Current production robots.txt misses bare protected paths | Chrome fetched two agent groups with public crawling allowed and the apex sitemap advertised. The restrictions used only patterns such as `/admin/`, leaving the bare path unmatched. The current checkout already defines exact-path and descendant rules in a single wildcard group. |

Vercel's [project domains](https://vercel.com/param96s-projects/param-portfolio/settings/domains) mark both custom hosts as valid and connected to Production. The project identifies the apex as its public URL, and the live 308 confirms the redirect direction. Keep `https://parampatel.in` canonical and retain the single application redirect. HTTPS worked on both hosts and both sampled responses carried HSTS. [Deployment Protection](https://vercel.com/param96s-projects/param-portfolio/settings/deployment-protection) uses Vercel Authentication with Standard Protection enabled. The Clerk publishable and secret keys are each scoped to Production and Preview in Vercel. The live development-instance handshake establishes the effective Clerk environment for sampled requests. Secret values were not viewed or changed.

## Repository configuration and changes

The checkout uses Next.js 16.3.0 with the App Router. The root layout defines a fixed production `metadataBase` and inherited robots and Googlebot directives. Landing pages and CMS article metadata supply their own canonicals. Admin and authentication metadata, intentional route-level HTTP headers, Clerk access checks, and missing-page exclusions remain in place. The repository has no `vercel.json`. `next.config.ts` contains the www, resume and legacy project redirects, PostHog rewrites, and route-scoped headers.

- `src/proxy.ts` limits Clerk's server handshake to protected routes, authentication routes, APIs and the Clerk endpoint. Public requests continue through the existing visit-tracking path to page rendering.
- `src/lib/seo.ts` and `src/app/opengraph-image.tsx` share the branded image URL, dimensions and alt text. Child Open Graph objects replace parent fields in Next.js, so public landing pages now attach that image explicitly. Twitter inherits the resolved Open Graph image.
- Landing page metadata changes are in `src/app/page.tsx`, `src/app/projects/page.tsx`, `src/app/blog/page.tsx`, `src/app/research/page.tsx`, `src/app/ai-lab/page.tsx` and `src/app/contact/layout.tsx`.
- `src/app/blog/[slug]/page.tsx`, `src/app/research/[slug]/page.tsx` and `src/sanity/lib/queries.ts` resolve editorial social images from published Sanity data with the branded fallback. Blog articles can also use their existing cover image.
- `scripts/validate_seo.py` reports navigation and header failures independently of sitemap failures. It checks both user-agent profiles for each public page, requires explicit robots directives and HTTPS social images, checks same-site image responses, finds linked articles missing from the sitemap, and verifies redirect hop limits and query preservation. `scripts/test_seo_validator.py` tests the expanded behavior.
- This report records the live evidence and deployment handoff.

The checked-in robots and sitemap generators are `src/app/robots.ts` and `src/app/sitemap.ts`. The sitemap uses the published Sanity perspective, shares article eligibility with the public pages, and includes only the six landing routes plus eligible blog and research details. The About content lives on the homepage. The repository has no About route or individual project page. Legacy project URLs redirect to the projects listing. Neither they nor the resume redirect belong in the HTML sitemap.
